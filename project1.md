# Telehealth Patient Management Database

A relational database design and SQL analysis project for a telehealth organization, built for **MIST 4610** at the University of Georgia (Terry College of Business). The database tracks patients, providers, appointments, billing, insurance, prescriptions, and patient-provider communications, and the SQL queries turn that data into insights managers can act on.

**Author:** Aidan Pfeiffer (team project)

## Skills Demonstrated

- Relational database design (primary/foreign keys, normalization)
- Data dictionary documentation
- SQL: `JOIN`, `GROUP BY`, `HAVING`, aggregate functions, `NOT EXISTS`, correlated subqueries, nested subqueries
- Translating business questions into SQL

## Data Model

The database has 11 tables:

| Table | Purpose | Key |
|---|---|---|
| `Patients` | Patient demographics and contact info | `patientID` (PK) |
| `Provider` | Providers (NPs, psychiatrists, MDs, DOs) | `providerID` (PK) |
| `MedicalEncounters` | Appointments between patients and providers | `encounterID` (PK); FKs: `patientID`, `providerID` |
| `MedicalRecords` | Test results, conditions, immunizations | `patientID` (PK/FK) |
| `Prescriptions` | Medications prescribed to patients | `prescriptionID` (PK); FKs: `patientID`, `providerID` |
| `Communications` | Messages/calls between patients and providers outside of appointments | `messageID` (PK); FKs: `patientID`, `providerID` |
| `Invoice` | Amounts owed, generated by encounters | `invoiceID` (PK); FK: `encounterID` |
| `Payments` | Payments made against invoices | `checkNo` (PK); FKs: `patientID`, `invoiceID`, `customerInsuranceID` |
| `InsuranceProvider` | Insurance companies | `insuranceProvider` (PK) |
| `InsurancePlan` | Plans offered by each insurance company, with prescription coverage % | `planID` (PK); FK: `insuranceProvider` |
| `CustomerInsurance` | Enrollment of a patient in an insurance plan | `customerInsuranceID` (PK); FKs: `planID`, `patientID` |

### Relationships

- A **patient** has many **encounters**, **prescriptions**, **communications**, and **payments**, and one **medical record**.
- A **provider** handles many **encounters**, writes many **prescriptions**, and takes part in many **communications**.
- Each **encounter** generates **invoices**, and each invoice can receive **payments**.
- A **patient** enrolls in **insurance plans** through `CustomerInsurance`; each plan belongs to an **insurance provider**.

## SQL Queries

Each query answers a business question for telehealth managers. Each one is labeled simple (basic filtering, sorting, and counting) or complex (subqueries, joins across several tables, and aggregation with `HAVING`).

### 1. Patients with no messages (simple)

**Business question:** Which patients have never contacted their providers outside of an appointment?

**Why it matters:** Patients who never message may be less engaged. Managers can use this list for follow-ups, reminders, or outreach campaigns to improve patient satisfaction.

**Concepts:** `NOT EXISTS`, correlated subquery

```sql
SELECT Patients.patientFname, Patients.patientLname
FROM Patients
WHERE NOT EXISTS (
    SELECT *
    FROM Communications
    WHERE Communications.patientID = Patients.patientID
);
```

The `NOT EXISTS` condition checks whether a matching `patientID` appears in `Communications`. If none does, the patient is included in the results.

### 2. Patients with no messages, alternate approach (simple)

**Business question:** Same as above, solved with a different technique.

**Concepts:** `LEFT JOIN`, `IS NULL` anti-join

```sql
SELECT Patients.patientFname, Patients.patientLname
FROM Patients
LEFT JOIN Communications
    ON Communications.patientID = Patients.patientID
WHERE Communications.messageID IS NULL;
```

Every patient is kept by the `LEFT JOIN`. Patients with no matching communication have a `NULL` `messageID`, which is what the `WHERE` clause filters for.

### 3. Highest-paying patients (complex)

**Business question:** Which patients have paid at or above the average total payment per patient?

**Why it matters:** Identifying the highest-paying patients lets managers focus resources on keeping them well served, which builds loyalty to the programs and strengthens relationships with important patients.

**Concepts:** `JOIN`, `GROUP BY`, `HAVING`, nested subquery, `SUM`, `AVG`

```sql
SELECT patientFname, patientLname, SUM(Payments.amount) AS totalPaid
FROM Patients
JOIN Payments ON Patients.patientID = Payments.patientID
GROUP BY Patients.patientID, patientFname, patientLname
HAVING SUM(Payments.amount) >= (
    SELECT AVG(total_per_patient)
    FROM (
        SELECT SUM(amount) AS total_per_patient
        FROM Payments
        GROUP BY patientID
    ) AS PatientTotals
);
```

The inner query totals payments per patient, the middle query averages those totals, and the outer query keeps only patients whose total meets or exceeds that average.

### 4. Patient contact list (simple)

**Business question:** What is the contact information (name, phone, email) for every patient?

**Why it matters:** Gives staff a quick directory for appointment reminders and outreach.

**Concepts:** `SELECT`

```sql
SELECT patientFname, patientLname, phone, email
FROM Patients;
```

### 5. Scheduled encounters (simple)

**Business question:** Which medical encounters are currently marked as "Scheduled"?

**Why it matters:** Lets managers see upcoming appointments and plan provider workloads.

**Concepts:** `WHERE`

```sql
SELECT encounterID, patientID, providerID, apptDate
FROM MedicalEncounters
WHERE apptStatus = 'Scheduled';
```

### 6. High-balance invoices (simple)

**Business question:** Which patients have invoices over $3,000, from smallest to largest?

**Why it matters:** The finance team can identify higher balances and prioritize follow-up actions.

**Concepts:** `JOIN`, `WHERE`, `ORDER BY`

```sql
SELECT patientFname, patientLname, Invoice.amount
FROM Patients
JOIN MedicalEncounters ON Patients.patientID = MedicalEncounters.patientID
JOIN Invoice ON MedicalEncounters.encounterID = Invoice.encounterID
WHERE Invoice.amount > 3000
ORDER BY Invoice.amount ASC;
```

### 7. Insurance plans per insurance company (simple)

**Business question:** How many plans does each insurance company offer within the accepted network?

**Why it matters:** Management can see which insurance companies are most prominent in the organization's accepted plan network.

**Concepts:** `COUNT`, `GROUP BY`

```sql
SELECT insuranceProvider, COUNT(*) AS numPlans
FROM InsurancePlan
GROUP BY insuranceProvider
ORDER BY numPlans DESC;
```

### 8. Communications log (simple)

**Business question:** What messages have been exchanged between providers and patients?

**Why it matters:** Provides a complete record of patient-provider communication outside of appointments.

**Concepts:** `SELECT`, `ORDER BY`

```sql
SELECT messageID, messageContent, providerID, patientID
FROM Communications
ORDER BY messageID ASC;
```

### 9. Prescriptions for a single patient (simple)

**Business question:** What prescriptions have been written for a specific patient?

**Why it matters:** Gives providers a quick view of one patient's medication history. Replace `1` with the patient ID of interest.

**Concepts:** `WHERE`

```sql
SELECT prescriptionID, medicationName, patientID, providerID
FROM Prescriptions
WHERE patientID = 1;
```

### 10. Total billed vs. total paid per patient (complex)

**Business question:** For each patient, how much have they been billed and how much have they paid, including patients with no payments?

**Why it matters:** Highlights outstanding balances across the patient base.

**Concepts:** Correlated subqueries, `SUM`

```sql
SELECT patientID, patientFname, patientLname,
    (SELECT SUM(amount)
     FROM Invoice
     WHERE encounterID IN (
         SELECT encounterID
         FROM MedicalEncounters
         WHERE patientID = Patients.patientID
     )) AS totalBilled,
    (SELECT SUM(amount)
     FROM Payments
     WHERE patientID = Patients.patientID) AS totalPaid
FROM Patients;
```

Patients with no payments show `NULL` for `totalPaid`.

### 11. Active insurance coverage (complex)

**Business question:** Which patients currently have unexpired insurance coverage, and under which plan?

**Why it matters:** Helps billing staff confirm coverage before invoicing and flag patients whose coverage has lapsed.

**Concepts:** `JOIN`, correlated subqueries, date filtering

```sql
SELECT patientFname, patientLname,
    (SELECT planName
     FROM InsurancePlan
     WHERE planID = CustomerInsurance.planID) AS planName,
    (SELECT coverage
     FROM InsurancePlan
     WHERE planID = CustomerInsurance.planID) AS coverage,
    policyNumber,
    expirationDate
FROM Patients, CustomerInsurance
WHERE Patients.patientID = CustomerInsurance.patientID
  AND expirationDate > CURDATE();
```

### 12. Busiest provider (complex)

**Business question:** Which provider has handled the most medical encounters, and how many?

**Why it matters:** Shows workload distribution and helps with staffing and capacity planning.

**Concepts:** Subqueries, `GROUP BY`, `ORDER BY`, `LIMIT`

```sql
SELECT providerName,
    (SELECT COUNT(*)
     FROM MedicalEncounters
     WHERE MedicalEncounters.providerID = Provider.providerID) AS totalEncounters
FROM Provider
WHERE providerID = (
    SELECT providerID
    FROM MedicalEncounters
    GROUP BY providerID
    ORDER BY COUNT(*) DESC
    LIMIT 1
);
```

### 13. Patients paying above the average (complex)

**Business question:** Which patients' total payments are strictly greater than the average total per patient?

**Why it matters:** Identifies patients who contribute the most revenue, which can inform future business strategy.

**Concepts:** `JOIN`, `GROUP BY`, `HAVING`, nested subquery

```sql
SELECT patientFname, patientLname, SUM(Payments.amount) AS totalPaid
FROM Patients
JOIN Payments ON Patients.patientID = Payments.patientID
GROUP BY Patients.patientID, patientFname, patientLname
HAVING SUM(Payments.amount) > (
    SELECT AVG(total_per_patient)
    FROM (
        SELECT SUM(amount) AS total_per_patient
        FROM Payments
        GROUP BY patientID
    ) AS PatientTotals
);
```

### 14. Invoices with no payments (complex)

**Business question:** Which patients have invoices that have received no payment at all?

**Why it matters:** The finance team can identify unpaid balances and focus on follow-up actions.

**Concepts:** `JOIN`, `NOT EXISTS`

```sql
SELECT patientFname, patientLname, Invoice.invoiceID, Invoice.amount
FROM Patients
JOIN MedicalEncounters ON Patients.patientID = MedicalEncounters.patientID
JOIN Invoice ON MedicalEncounters.encounterID = Invoice.encounterID
WHERE NOT EXISTS (
    SELECT *
    FROM Payments
    WHERE Payments.invoiceID = Invoice.invoiceID
);
```

### 15. Patients and their prescriptions, including none (complex)

**Business question:** What prescriptions does each patient have, including patients who have never received one?

**Why it matters:** Gives a complete patient list with medication information, making it easy to spot patients with no prescriptions.

**Concepts:** `LEFT JOIN`, `ORDER BY`

```sql
SELECT
    pa.patientID,
    pa.patientFname,
    pa.patientLname,
    pr.prescriptionID,
    pr.medicationName
FROM Patients pa
LEFT JOIN Prescriptions pr ON pa.patientID = pr.patientID
ORDER BY pa.patientLname, pa.patientFname, pr.prescriptionID;
```

A `LEFT JOIN` keeps patients without prescriptions, and results are sorted by patient name, then prescription ID.

### 16. Repeat patient-provider relationships (complex)

**Business question:** Which patients have had more than one encounter with the same provider?

**Why it matters:** Reveals repeat patient-provider relationships, which can indicate continuity of care.

**Concepts:** `JOIN`, `GROUP BY`, `HAVING`

```sql
SELECT
    pa.patientID,
    pa.patientFname,
    pa.patientLname,
    pr.providerID,
    pr.providerName,
    COUNT(me.encounterID) AS totalEncounters
FROM MedicalEncounters me
JOIN Patients pa
    ON me.patientID = pa.patientID
JOIN Provider pr
    ON me.providerID = pr.providerID
GROUP BY
    pa.patientID,
    pa.patientFname,
    pa.patientLname,
    pr.providerID,
    pr.providerName
HAVING COUNT(me.encounterID) > 1;
```

The query joins the three tables, counts visits per patient-provider pair, and `HAVING` keeps only pairs with more than one visit.

## Notes

- This project was built and tested in MySQL (`CURDATE()`-style syntax).
- `Communications` links a patient and a provider but does not record who sent each message, so "no messages" means no communications on record for that patient.
