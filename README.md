# Telehealth Patient Management Database

A relational database design and SQL analysis project for a telehealth organization, built for **MIST 4610** at the University of Georgia (Terry College of Business). The database tracks patients, providers, appointments, billing, insurance, prescriptions, and patient-provider communications, and the SQL queries turn that data into insights managers can act on.

**Author:** Aidan Pfeiffer

## Skills Demonstrated

- Relational database design (primary/foreign keys, normalization)
- Data dictionary documentation
- SQL: `JOIN`, `GROUP BY`, `HAVING`, aggregate functions, `NOT EXISTS`, correlated subqueries, nested subqueries
- Translating business questions into SQL

## Data Model

The database has 11 tables:

| Table | Purpose | Key |
|---|---|---|
| `Patients` | Patient demographics and contact info | `patientID` (PK) |
| `Provider` | Providers (NPs, psychiatrists, MDs, DOs) | `providerID` (PK) |
| `MedicalEncounters` | Appointments between patients and providers | `encounterID` (PK); FKs: `patientID`, `providerID` |
| `MedicalRecords` | Test results, conditions, immunizations | `patientID` (PK/FK) |
| `Prescriptions` | Medications prescribed to patients | `prescriptionID` (PK); FKs: `patientID`, `providerID` |
| `Communications` | Messages/calls between patients and providers outside of appointments | `messageID` (PK); FKs: `patientID`, `providerID` |
| `Invoice` | Amounts owed, generated by encounters | `invoiceID` (PK); FK: `encounterID` |
| `Payments` | Payments made against invoices | `checkNo` (PK); FKs: `patientID`, `invoiceID`, `customerInsuranceID` |
| `InsuranceProvider` | Insurance companies | `insuranceProvider` (PK) |
| `InsurancePlan` | Plans offered by each insurance company, with prescription coverage % | `planID` (PK); FK: `insuranceProvider` |
| `CustomerInsurance` | Enrollment of a patient in an insurance plan | `customerInsuranceID` (PK); FKs: `planID`, `patientID` |

### Relationships

- A **patient** has many **encounters**, **prescriptions**, **communications**, and **payments**, and one **medical record**.
- A **provider** handles many **encounters**, writes many **prescriptions**, and takes part in many **communications**.
- Each **encounter** generates **invoices**, and each invoice can receive **payments**.
- A **patient** enrolls in **insurance plans** through `CustomerInsurance`; each plan belongs to an **insurance provider**.

## SQL Queries

Each query answers a business question for telehealth managers.

### 1. Patients with no messages (simple)

**Business question:** Which patients have never contacted their providers outside of an appointment?

**Why it matters:** Patients who never message may be less engaged. Managers can use this list for follow-ups, reminders, or outreach campaigns to improve patient satisfaction.

**Concepts:** `NOT EXISTS`, correlated subquery

```sql
SELECT Patients.patientFname, Patients.patientLname
FROM Patients
WHERE NOT EXISTS (
    SELECT *
    FROM Communications
    WHERE Communications.patientID = Patients.patientID
);
```

The `NOT EXISTS` condition checks whether a matching `patientID` appears in `Communications`. If none does, the patient is included in the results.

### 2. Patients with no messages, alternate approach (simple)

**Business question:** Same as above, solved with a different technique.

**Concepts:** `LEFT JOIN`, `IS NULL` anti-join

```sql
SELECT Patients.patientFname, Patients.patientLname
FROM Patients
LEFT JOIN Communications
    ON Communications.patientID = Patients.patientID
WHERE Communications.messageID IS NULL;
```

Every patient is kept by the `LEFT JOIN`. Patients with no matching communication have a `NULL` `messageID`, which is what the `WHERE` clause filters for.

### 3. Highest-paying patients (complex)

**Business question:** Which patients have paid at or above the average total payment per patient?

**Why it matters:** Identifying the highest-paying patients lets managers focus resources on keeping them well served, which builds loyalty to the programs and strengthens relationships with important patients.

**Concepts:** `JOIN`, `GROUP BY`, `HAVING`, nested subquery, `SUM`, `AVG`

```sql
SELECT patientFname, patientLname, SUM(Payments.amount) AS totalPaid
FROM Patients
JOIN Payments ON Patients.patientID = Payments.patientID
GROUP BY Patients.patientID, patientFname, patientLname
HAVING SUM(Payments.amount) >= (
    SELECT AVG(total_per_patient)
    FROM (
        SELECT SUM(amount) AS total_per_patient
        FROM Payments
        GROUP BY patientID
    ) AS PatientTotals
);
```

The inner query totals payments per patient, the middle query averages those totals, and the outer query keeps only patients whose total meets or exceeds that average.

## Notes

- This project was built and tested in MySQL (`CURDATE()`-style syntax).
- `Communications` links a patient and a provider but does not record who sent each message, so "no messages" means no communications on record for that patient.
